# DRAW-1: carry a metrics-free ink class per plan row so apply stops rescanning every cell

Source: `docs/scratch/2026-08-18-construction-audit.md` DRAW-1 (absorbs FRAME-2),
verified against master after FRAME-1 (`3bea76c5`). This plan pivots from the
audit's ideal (pixel reach as a plan field) to the split research/33 D9 already
names: a per-row ink *class* in the plan, a per-metrics envelope in the store.

## Problem

`TerminalFrameBackingStore.apply` -- the incremental render path, once per
presented frame -- calls `renderRowReaches(of: plan, ...)` on the complete plan
(`TerminalFrameBackingStore.swift#apply`). That function visits every text cell
of every row and classifies its scalar (`RenderInkReach.swift#renderRowReaches`).
At 179x66 that is ~11.8k cell visits per frame, to learn reaches `apply` reads
only at the damaged rows and their one-row neighborhood. A 4-row damage pays the
whole-viewport scan; FRAME-1 made the loop row-indexed but left the cost.

Evidence:

- `apply` passes no damage to `renderRowReaches`; `renderApplyShape` reads
  `newReaches` at damaged rows and rows within one of an erase span; `apply`
  merges `newReaches[row]` into the store's ledger only for damaged rows.
- `renderFull` calls the same function; `scripts/research/33/t5-scroll-amplification-probe.swift`
  calls it with the same signature to mirror the store, and already plans
  through `PaneFramePlanner`.

Load-bearing premises:

- A row's ink class is a pure function of that row's runs: printable-ASCII
  single-scalar cells are submitted unclipped from the measured tables (reach =
  envelope); any other single-scalar cell may be submitted unclipped from a
  wider cmap (reach = one full cell past both edges); multi-scalar cells and
  every background/overlay/decoration run are clipped or exact (reach = the
  band). Pixel reach is that class mapped through the metrics' envelope and
  cell height (research/33 D9, "per-row ink classes over a per-metrics measured
  envelope").
- The planner sees no metrics and must not: it runs inside `TerminalPaneSession`
  (`lib/TerminalPTY`), `TerminalRenderPlanning.swift` states pixel geometry stays
  app-side, and `PaneFramePlanner` keys reuse on `RenderPresentation` alone. The
  swapchain is replaced whole on any metrics change, so a plan reused across a
  metrics change would hand stale pixel reaches to a fresh store -- the hazard
  the audit's own "sharper ideal" names. A metrics-free class has no such
  hazard.
- Undamaged rows copy forward in `FramePlanner.plan(reusing:damage:)` and
  shifted rows are translated (row field only; payload arrays shared). A class
  that describes content, not position, rides both unchanged.
- `RenderPlanRow` is constructed only inside `RenderFramePlanner.swift`; no
  test or other target builds one by hand, and the only hand-assembled plan in
  the tests passes existing rows through. The cursor is a frame-level record on
  the plan, not a row's content.

## Decision

Add a per-row ink class to `RenderPlanRow`, produced when the row is planned and
carried through copy-forward and translation. `renderRowReaches(of:envelope:cellHeightPixels:)`
keeps its public signature and return type and becomes O(rows): it maps each
row's class through the envelope and cell height and adds the cursor's band from
`plan.cursor`. The store's pixel ledger, `renderTranslationStaleStrips`, and
`renderApplyShape` do not change.

Behavioral scope: no pixel changes anywhere. `apply` and `renderFull` draw the
same bytes; the t5 probe and every caller of `renderRowReaches` compile and
behave unchanged. The iOS client (`planFrame` + `renderFull` only) is untouched
and gets a cheaper `renderFull`.

Decisive constraints:

- The class is a set of facts (has ASCII single-scalar text, has other
  single-scalar text, has band content), not a three-valued ordering: the
  envelope's top margin can be positive, so an ASCII-only row's reach starts
  below a band row's, and the row's reach is the union of the facts present.
- The class belongs to the row's content. Translation and copy-forward carry
  it; neither re-inspects cells. A scroll of 65 undamaged rows must not rescan
  them.
- Pixel conversion (envelope, cell height, nil-envelope degradation, the
  one-cell clamp) stays with the metrics owner. The planning module gains no
  pixel input.

## Invariants

- I1. A plan's row runs and row ink classes cannot disagree: the class is
  produced by the same pass that produces the runs, and a reused or translated
  row has the class of the row it copies.
- I2. `renderRowReaches(of:envelope:cellHeightPixels:)` returns, for every plan,
  exactly what it returns today: for each row, the union over its content of
  {envelope reach for ASCII single-scalar cells, full-cell halo for other
  single-scalar cells, band for everything else drawn, band for the cursor
  row}; nil for a row that draws nothing; nil envelope degrades ASCII to the
  full-cell halo.
- I3. A plan reused across damage (and across a recorded shift) yields the same
  reaches as a fresh plan of the same terminal state.
- I4. An apply-rendered store stays byte-identical to a from-scratch render of
  the same plan -- including when the plans it applies came through
  `PaneFramePlanner` reuse, which is the production path and the one that
  carries the class.
- I5. `renderRowReaches` does not visit cells: its cost is proportional to the
  row count, not the cell count.

## Proof obligations

- PO1 (I2): the existing reach tests in `RenderInkReachTests.swift` (ASCII,
  general, cluster, empty/band, cursor, nil envelope) pass unchanged -- same
  entry point, same expected values. These are the classifier's proof for
  fresh rows; a reused-equals-fresh check cannot be, since both sides run the
  same classifier.
- PO2 (I3): reaches of a plan produced through `PaneFramePlanner` with partial
  damage equal reaches of `planFrame` on the same terminal, over (a) an
  undamaged row copied forward, (b) rows translated by a recorded shift
  (streaming, a DECSTBM region scroll), (c) a damaged row transitioning ASCII
  -> accented -> ASCII, whose reach visibly changes class at each step, and (d)
  a band appearing and disappearing on an otherwise empty row. Each scenario
  must assert that reuse actually happened (partial damage, a non-zero shift)
  so it cannot pass vacuously.
- PO3 (I1, I3): a reused plan equals a fresh plan of the same terminal state
  (`RenderFramePlan` equality); the existing pane-planning, shift-damage, and
  corpus sweep equality pins cover this and stay green.
- PO4 (I4): the byte-exactness pins in `FrameBackingStoreTests.swift` pass
  unchanged, and the same store-equals-full-render assertion is also driven
  with plans from `PaneFramePlanner` over the streaming, mixed-content,
  class-transition, and region-edge scenarios. Today every pin plans each
  step with `planFrame`, so no pixel test yet feeds a reuse-carried class into
  the store; this closes that gap.
- PO5 (I5): not a unit test. Pre-registered reading, per
  `agent-docs/measurement-discipline.md`: the win instrument is
  `just benchmark-trace btop-scroll "Time Profiler" 20` -- `renderRowReaches`
  loses essentially all self time in `profile-report.json`, which is the proof
  that the cell scan left the draw path. On
  `just benchmark-quick baseline=HEAD workload=content-churn` (full damage),
  read and record the `plan time:` verdict and the draw verdict separately,
  each under its own calibrated rule; neither offsets the other, and a move in
  one is never evidence about the other. The planner-side classification cost
  that a `plan time:` regression would report is the relocation AR1 accepts in
  advance. `incremental-mixed` is descriptive only and decides nothing. Read a
  control the change cannot reach (the drain line) in the same session.

## Non-goals

- Moving pixel reach, the envelope, or cell height into the planner or the
  reuse key.
- Narrowing `renderRowReaches` to a row set (the audit's cheaper fallback):
  unnecessary once the function is O(rows).
- FRAME-3's `rowIndices` -> spans change in `apply`; MOBILE-2's adoption of
  `apply` on the phone. Both follow this item.
- Editing research/33 F27: it is a dated record of the T14 landing and stays
  as written.

## Accepted risks

- AR1. On full-damage workloads the per-cell classification moves from the
  store's render into the planner's row pass; total per-frame work is
  unchanged, only relocated, and the plan-time line may report it as a
  regression (PO5 reads that line on its own terms). Accepted because the incremental path -- the one whose
  purpose is to touch a handful of rows -- stops paying it entirely.

## Rejected ideas

- RI1. Publish `rowReaches: [RenderRowReach?]` on `RenderFramePlan` (the audit's
  ideal). Puts pixels into a metrics-free module and forces metrics into the
  planner's reuse key, a coupling nothing in `lib/TerminalPTY` has today.
- RI2. Keep the whole-plan scan but only at damaged rows plus neighbors, merged
  into the store's ledger (FRAME-2's form). Leaves reach derived by two owners
  and re-scanned per apply rather than once per replanned row.

## Implementation discretion

- Where the class is derived -- in `RenderPlanRow`'s initializer from its runs
  (then the translated-row rebuild must copy the class rather than re-derive
  it), or accumulated in the planner's per-cell pass and passed in -- provided
  I1 and the no-rescan-on-translation constraint both hold.
- The class's representation (option set vs. three booleans) and whether it is
  a public stored field or read through an accessor.

## Deliverables beyond code

- Doc comments that now misstate the mechanism move with it: the
  `renderRowReaches` header ("classifies every row" -> maps each row's class)
  and the `RenderPlanRow` doc (the class's contract, citing D9).
- The audit's DRAW-1 checklist entry flips to done with the commit hash, as
  FRAME-1's did.

## Implementation notes

- `RenderRowInkClass` is an option set accumulated in the planner's existing
  cell traversal. This preserves fact unions without ordering the ASCII,
  general-text, and band cases. Translation copies the set with its row.
- The pre-commit `content-churn` quick comparison classified plan time as
  20.66% slower over two pairs (+22.84%, +18.48%), while draw time was
  equivalent at -0.81%. A post-commit confirm comparison against the same
  baseline and production source did not reproduce the large plan-time move:
  its four pairs were +0.44%, +0.87%, +2.07%, and +2.56% (median +1.47%),
  while draw time was equivalent at +0.28%. Confirm-mode plan time is
  descriptive and uncalibrated, so it does not formally overturn the quick
  verdict. The disagreement does mean the implementation has no demonstrated
  stable end-to-end speedup or 20% planner regression. Its accepted result is
  structural: the apply path no longer performs the whole-plan cell scan, and
  the candidate profile attributed about 0.02% self time to
  `renderRowReaches`.
