# Plan: `danterm read-pane` -- read a pane's terminal text

## Context

DanTerm's CLI can write to other panes (the recent send-keys commit added
`--pane <id>` cross-pane targeting and tmux-style key tokens) but it can't
read from them. This plan adds the read direction: a `read-pane` subcommand
that captures the visible viewport, or the last N lines of scrollback, of a
specific pane.

Use cases:
- An agent in pane A wants to inspect what the user just ran in pane B.
- Smoke tests / shell scripts asserting on terminal output without mucking
  with the pty.
- Future work (out of scope here) like "pipe-pane" / scripted hooks.

Libghostty already exposes everything we need (`ghostty_surface_read_text`,
`ghostty_surface_free_text`, `ghostty_selection_s`, `GHOSTTY_POINT_*`); the
codebase even has one in-tree caller (`AppRuntime.readScrollbackText` for
session checkpoints). The work is just CLI surface + IPC handler + an
Effect that the runtime performs against the resolved surface.

## CLI shape

```
danterm read-pane --pane <uuid> [--lines <n>]
```

- `--pane <uuid>` -- required. No `$DANTERM_PANE` fallback (caller is always
  asking about some specific pane, often not their own).
- `--lines <n>` -- optional, positive int. If omitted, returns just the
  visible viewport. If present, returns the last `n` lines of the full
  written content (scrollback + visible).
- stdout -- the captured text, byte-for-byte. No JSON wrapping, no extra
  trailing newline added by the CLI (the captured text already ends with
  whatever the terminal had).
- Exit status -- 0 on success, 1 on any error (unknown pane, bad args, IPC
  failure, capture failure). Errors go to stderr in the existing
  `danterm: <message>` format.

## Capture model (two tags)

Per Ghostty's own point-tag docs (`.ghostty-src/src/terminal/point.zig:11-48`):

- `viewport` -- top-left is the visible viewport top, bottom-right is the
  last written row from there. Right tag for "what's on screen".
- `screen` -- top-left is the furthest-back scrollback row, bottom-right is
  the last written row anywhere. Right tag for "everything written, no
  trailing blanks". Crucially, this stops at the last written row -- it
  does *not* include the unwritten padding that `active` includes.
- `active` and (history-aliased) `surface` are deliberately not used here.
  `active`'s bottom-right pads to the full screen height with unwritten
  rows, which would inflate captures with blank trailing lines.

Mapping:

- `--lines` omitted -> read once with `GHOSTTY_POINT_VIEWPORT`, return as-is.
- `--lines N` -> read once with `GHOSTTY_POINT_SCREEN`, then tail to the
  last `N` lines.

A single read per request, single tag. No multi-tag heuristic, no
longest-result picking, no merging.

### `lib/DanTermProtocol/Sources/DanTermProtocol/ReadPaneArgs.swift` (new)

Mirrors the `SendKeysArgs.swift` precedent so the CLI's argv parsing has a
single, testable home. Two pure helpers and their error type:

```swift
public struct ParsedReadPane: Equatable {
    public let pane: String        // CLI-side: pre-validation, just non-empty.
    public let lineLimit: Int?     // > 0 when present.
}

public enum ReadPaneParseError: Error, Equatable {
    case missingPane              // --pane never provided
    case missingPaneArg           // --pane with no following value
    case missingLinesArg          // --lines with no following value
    case invalidLines(String)     // --lines value not a positive int
    case unknownFlag(String)      // any --foo we don't recognize
    case unexpectedArgument(String) // bare positional arg
}

public func parseReadPaneArgs(_ args: [String]) throws -> ParsedReadPane

// Pulls "text" out of the JSON-RPC result object. Returns nil if the
// result is malformed. Used by the CLI to render to stdout without an
// extra terminator -- the caller writes exactly what comes back.
public func renderReadPaneResult(_ result: JSONValue) -> String?
```

Plus a pure helper that's needed by AppRuntime when `--lines` is set:

```swift
// Returns the last `n` lines of `text`. Preserves a trailing newline when
// the input has one. n <= 0 returns "". If the input has fewer than n
// lines, returns the original text unchanged.
public func tailLines(_ text: String, n: Int) -> String
```

`tailLines` lives in the protocol module so it can be tested in
`DanTermProtocolTests` without spinning up Cocoa or Ghostty. AppRuntime
imports it.

### `lib/DanTermProtocol/Tests/DanTermProtocolTests/ReadPaneArgsTests.swift` (new)

Behavioral, structure-insensitive XCTest cases:

**Parser:**
- `--pane <uuid>` only -> `ParsedReadPane(pane: uuid, lineLimit: nil)`.
- `--pane <uuid> --lines 50` -> `lineLimit == 50`.
- `--lines 50 --pane <uuid>` -> same result (flag order doesn't matter).
- No flags -> `.missingPane`.
- `--pane` with nothing after -> `.missingPaneArg`.
- `--pane ""` -> `.missingPane` (empty rejected).
- `--lines` with nothing after -> `.missingLinesArg`.
- `--lines 0`, `--lines -5`, `--lines abc`, `--lines 1.5` -> `.invalidLines(...)`.
- `--frob` -> `.unknownFlag("--frob")`.
- Bare `foo` -> `.unexpectedArgument("foo")`.

**Renderer:**
- `{ "text": "hello" }` -> `"hello"`.
- `{ "text": "a\nb\nc\n" }` -> `"a\nb\nc\n"` (trailing newline preserved
  byte-for-byte).
- `{ "text": "" }` -> `""`.
- `{ }`, `{ "text": 42 }`, `[1, 2]`, top-level non-object -> `nil`.

**`tailLines`:**
- `tailLines("a\nb\nc\nd\n", n: 2)` -> `"c\nd\n"` (trailing newline kept).
- `tailLines("a\nb\nc", n: 2)` -> `"b\nc"` (no trailing newline; none added).
- `tailLines("a\nb", n: 5)` -> `"a\nb"` (n exceeds line count; full input).
- `tailLines("", n: 1)` -> `""`.
- `tailLines("hello\n", n: 1)` -> `"hello\n"`.
- `tailLines("a\nb\nc\nd", n: 1)` -> `"d"`.
- `tailLines("a\nb\n", n: 0)` -> `""`.

### `app/Update.swift`

Add a case in `handleIpcRequest` (next to `Methods.sendKeys` at line 1501).
Single source of truth for input validation:

```swift
case Methods.readPane:
    do {
        guard case .object(let object) = params else {
            throw IpcParamsError("invalid params")
        }
        // Pane: required string, must parse, must exist.
        guard case .string(let raw)? = object["pane"] else {
            throw IpcParamsError("pane required")
        }
        guard let paneId = parsePaneId(raw), model.panes[paneId] != nil else {
            throw IpcParamsError("pane not found")
        }
        // Lines: optional positive int.
        let lineLimit: Int?
        switch object["lines"] {
        case .none, .null:
            lineLimit = nil
        case .number(let n):
            guard let i = Int(exactly: n), i > 0 else {
                throw IpcParamsError("lines must be a positive integer")
            }
            lineLimit = i
        default:
            throw IpcParamsError("lines must be a positive integer")
        }
        return [.readPaneText(reqId: reqId, paneId: paneId, lineLimit: lineLimit)]
    } catch let error as IpcParamsError {
        return ipcInvalidParams(reqId, error.message)
    } catch {
        return ipcInvalidParams(reqId, "invalid params")
    }
```

Note the handler returns *only* `.readPaneText` -- no `.ipcReply` here.
The reply is emitted by the runtime once the read completes (the runtime
already owns the connection map at `ipcConnections`).

### `app/AppRuntime.swift`

1. Add the `.readPaneText` performer in the `perform(_:)` switch
   (line 304). It runs on `MainActor` like every other Ghostty call.
   Failure paths are explicit: pane gone -> `-32603 "pane no longer
   available"`; underlying read failed -> `-32603 "failed to read pane
   text"`. We do not coerce nil to empty string -- the caller needs to
   tell capture-failure apart from a legitimately-empty pane:

```swift
case .readPaneText(let reqId, let paneId, let lineLimit):
    guard let connection = ipcConnections.removeValue(forKey: reqId) else { break }
    guard let surface = surfaces[paneId]?.surface else {
        connection.writeError(reqId: reqId, code: -32603, message: "pane no longer available")
        break
    }
    guard let text = capturePaneText(surface: surface, lineLimit: lineLimit) else {
        connection.writeError(reqId: reqId, code: -32603, message: "failed to read pane text")
        break
    }
    connection.writeSuccess(reqId: reqId, result: .object(["text": .string(text)]))
```

2. Refactor surface reading into a small primitive plus a typed entry
   point. Both return `String?` -- the caller is responsible for treating
   `nil` as failure (matching the existing `readScrollbackText` shape):

```swift
// Single read with one point tag, TOP_LEFT to BOTTOM_RIGHT.
// Returns nil iff ghostty_surface_read_text returns false or UTF-8
// decoding fails. Returns "" when the region is empty (success but no
// content).
private func readSurfaceRegion(
    surface: ghostty_surface_t,
    tag: ghostty_point_tag_e
) -> String? { ... }

// Two-tag capture for IPC reads. VIEWPORT for visible-only,
// SCREEN for "everything written, no trailing blanks", then tail to N.
private func capturePaneText(
    surface: ghostty_surface_t,
    lineLimit: Int?
) -> String? {
    let tag: ghostty_point_tag_e = (lineLimit == nil)
        ? GHOSTTY_POINT_VIEWPORT
        : GHOSTTY_POINT_SCREEN
    guard let raw = readSurfaceRegion(surface: surface, tag: tag) else {
        return nil
    }
    guard let n = lineLimit else { return raw }
    return tailLines(raw, n: n)
}
```

3. The existing `readScrollbackText(surface:)` at line 749 collapses into a
   thin wrapper to preserve `enrichSnapshot`'s behavior at line 842 (which
   wants the full SCREEN region):

```swift
private func readScrollbackText(surface: ghostty_surface_t) -> String? {
    return readSurfaceRegion(surface: surface, tag: GHOSTTY_POINT_SCREEN)
}
```

   The selection geometry that was previously inlined moves into
   `readSurfaceRegion`; behavior at the enrich call site is preserved.

### `tests/UpdateIpcTests.swift`

Add a new `read-pane` section near the `send-keys` tests. Mirror the
helper style (`sendIpc`, `requireIpcReply`, `requireIpcError` at lines
583-623). Coverage:

- **Effect emission, viewport**: valid pane, no `lines` -> single
  `.readPaneText(_, paneId, nil)` effect, no `.ipcReply` (runtime owns
  the reply).
- **Effect emission, lines**: valid pane, `lines: 200` -> single
  `.readPaneText(_, paneId, 200)`.
- **Missing pane param**: -> `-32602` "pane required".
- **Pane param wrong type** (number, array, object): -> `-32602`.
- **Pane string but unparseable / not in model**: -> `-32602`
  "pane not found".
- **`lines` is zero**: -> `-32602` "lines must be a positive integer".
- **`lines` is negative**: -> `-32602`.
- **`lines` is a string**: -> `-32602`.
- **`lines` is a non-integer number** (e.g. `1.5`): -> `-32602`.

These cover both axes: the validation we add, and the claim that the
handler emits exactly one effect on success (no premature `.ipcReply`).
The actual surface read is in AppRuntime and isn't exercised by pure
tests -- there's no way to in-process call libghostty without a real
window. That's an acknowledged gap; manual verification covers it
end-to-end.

3. **Manual end-to-end** (in a DanTerm pane):
   ```
   # capture this pane's id
   echo $DANTERM_PANE

   # in pane A, run something visible
   ls -la

   # from any pane, read pane A's viewport
   danterm read-pane --pane <A-uuid>

   # tail last 50 lines of A's scrollback (SCREEN tag, then tail)
   danterm read-pane --pane <A-uuid> --lines 50

   # cross-pane: open a second pane (B), have it read A
   danterm read-pane --pane <A-uuid> --lines 200
   ```

   Expected: stdout is the actual visible/scrollback text of the target
   pane, terminating without an extra blank line. With `--lines N`, the
   output never contains trailing-blank padding (SCREEN stops at last
   written row).

4. **Error paths**:
   - `danterm read-pane`                            -> stderr "usage: ...", exit 1.
   - `danterm read-pane --pane`                     -> stderr "usage: ..." (missing-arg), exit 1.
   - `danterm read-pane --pane bogus`               -> stderr "pane not found", exit 1.
   - `danterm read-pane --pane <valid> --lines`     -> stderr "--lines must be a positive integer" (missing-arg), exit 1.
   - `danterm read-pane --pane <valid> --lines 0`   -> stderr "--lines must be a positive integer", exit 1 (rejected CLI-side).
   - `danterm read-pane --pane <valid> --lines -5`  -> same as above.
   - `danterm read-pane --pane <valid> --frob`      -> stderr "unknown flag: --frob", exit 1.

5. **Capture-failure path** (optional spot-check): in a debugger, set a
   breakpoint between `update()` returning the effect and `perform()`
   handling it; close the target pane in that window; confirm the caller
   gets a `-32603 "pane no longer available"` rather than a hang or
   silent empty success.

## Out of scope

- `--scrollback` flag (separate from `--lines`). Folded into `--lines` per
  the agreed UX.
- Streaming output / pipe-pane equivalent. Useful but a different shape
  than the one-shot RPC.
- HTML / ANSI-preserving capture. `ghostty_surface_read_text` returns
  plain text; preserving cell colors would require a different libghostty
  call and isn't asked for here.
- Falling back to `$DANTERM_PANE`. Explicitly rejected -- callers always
  pass an id.
