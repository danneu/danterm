# Headless `kitten-feed` benchmark arm

Source: research 39, Phase 2, task 1
(`docs/research/39-kitten-render-benchmark/README.md`). Evidence: `39/F1`,
`39/F3`, decision `39/D1`.

## Problem

`kitten __benchmark__ --render` shows DanTerm 2-5x behind Ghostty on four arms
(`ascii`, `unicode`, `unique_unicode`, `csi`), and `39/F1`/`39/F3` attribute
every one of them to `Terminal.feed` on the PTY-host thread at 98% CPU. The
A/B ladder (`just benchmark-quick` / `benchmark-confirm`) contains none of
these stimuli, so none of `H1`-`H4` can get a verdict. Phase 3 fixes are
blocked until an arm exists.

Load-bearing premises (verified):

- P1. The cost is inside `Terminal.feed`; drawing and PTY delivery are not on
  the profile (`39/F1`, `39/F3`, `read` is 3%). A headless replay measures the
  same thing kitten measures.
- P2. The generator is `references/kitty/tools/cmd/benchmark/main.go`
  (`39/D1`). `ascii` and `csi` draw from an unseeded `math/rand/v2`;
  `unicode` and `unique_unicode` are fully deterministic.
- P3. The ladder already has a headless feed workload shape: `terminal-feed`
  builds a fresh 179x66 `Terminal` per execution, feeds length-framed chunks,
  and reports duration-stable per-execution nanoseconds
  (`lib/TerminalCore/Sources/TerminalCoreBenchmark`,
  `scripts/terminal-benchmark-validation.py`). Its collector, block contract,
  manifest, and state probe are reusable as they stand.
- P4. `scripts/terminal-benchmark-candidate-screen.py` screens any name in
  `WORKLOADS | CANDIDATE_WORKLOADS` and writes a report, never a rule
  (`agent-docs/measurement-discipline.md`, "A screen is not a freeze").
- P5. The per-repetition reset and the alt-screen wrapper decide which scroll
  branch runs (`39/F1`: `rotatesWholeViewport` never runs on the alt screen),
  so the wrapper is part of the stimulus, not framing around it.

## Decision

Port the kitten generator to Swift, inside the `TerminalCore` package. The
Python collector generates each arm's fixture once, from the one immutable
root every fixture already comes from (`repository_root` in
`production_collectors`), and feeds the same framed bytes on stdin to both
arm binaries, exactly as `terminal-feed` does with its corpus. Four
candidate workloads enter the ladder, one per arm: `kitten-feed-ascii`,
`kitten-feed-unicode`, `kitten-feed-unique-unicode`, `kitten-feed-csi`. Each
is collected like `terminal-feed` (fresh 179x66 terminal per execution,
duration-stable batches, the same state probe and battery rule). The fixture
is split into an untimed setup, a timed portion, and an untimed teardown so
the harness times what kitten times. A `test-tooling` check holds the port to
the reference source.

Why this shape and not the alternatives:

- **Generate in Swift, once per collection, from one root -- not a
  committed fixture, not a Python port, and not inside each arm.** The
  bytes are 2 MiB per repetition and two arms are random, so a committed
  recording is not a fixture (`39/D1`). One port means the arm has one
  definition, and the profiling driver (`scripts/terminal-feed-profile.py`)
  gets the stream from the same place. Generating inside each measured
  binary would let a candidate change the bytes it parses without changing
  the identity and win a false verdict; the ladder's rule is that both arms
  receive identical stimulus from one immutable source, and the existing
  stdin-fed harness reads that stimulus once and reuses it for every
  execution.
- **Four workloads, not one.** `39` requires a verdict per arm on every fix;
  a combined stream would average `H4`'s `csi` win against three flat arms
  and hide it. Each workload owns its blocks and can be screened, frozen,
  and gated on its own.
- **Reuse the `terminal-feed` collector and contract rather than a new
  collector.** The block shape (fresh terminal per execution, one sample per
  block, floor of 1 s) is already calibrated in structure, and the only
  thing that differs is the byte source. A second collector would be a copy.

Behavioral scope: adds a generator library and a generate command on the
benchmark executable, a timing boundary in the harness's framed input, four
candidate workloads with block contracts and fixture identities, a tooling
lint, the `tools/tui/loop` directory in the kitty reference cone, and the
research doc's Phase 2 ledger entry. No decision rule is
frozen by this change. No `Terminal` code changes.

### The stream

Per arm, the generated bytes are structurally what kitten writes under
`--render` on the alt screen, in three portions that follow kitten's own
timer (`main.go`: `start := time.Now()` after the state write, `duration`
taken before the deferred restore):

1. Setup, untimed: alt-screen enter and cursor hide, the bytes kitten's
   `TerminalStateOptions{Alternate_screen: true}.SetStateEscapeCodes()` and
   `DECTCEM.EscapeCodeToReset()` emit (`tools/tui/loop`).
2. Timed: `--repetitions R` times the arm's payload followed by the reset
   `\x1b[m\x1b[H\x1b[2J` + `Running: <desc>\r\n`; then the tail
   `\x1b[m\x1b[H\x1b[2J` + `Waiting for response indicating parsing
   finished\r\n` + `\x1b[5n` x3.
3. Teardown, untimed: alt-screen leave, cursor show, and the
   `\x1b]\x1b\\\x1bc` reset, as kitten's deferred write sends them.

The harness feeds all three into one fresh terminal per execution and times
only portion 2. A change that only speeds up RIS or alt-screen teardown
cannot move the arm, because kitten does not measure it either.

Payloads match `main.go` exactly in alphabet, size, description string,
chunk table, and probability bands. The alphabet is kitten's indexed string
as written -- `ascii_printable` (86 entries, space twice) plus `\n\t`, 88
entries drawn by uniform index -- not the set of distinct bytes; `39/D1`'s
"94 printable ASCII characters" is wrong and the research doc is corrected
with this change. `unicode` and `unique_unicode` are
byte-identical to kitten's. `ascii` and `csi` replace the unseeded
`math/rand/v2` draws with a fixed-seed deterministic generator; the seed is
part of the fixture identity. Kitten's `Warmup` pass is not part of any arm.

`R` is a fixture parameter and appears in the identity. Kitten's default is
100; the arm does not need 100 to measure the same feed rate, because the
harness already scales executions to a 1 s floor. `R` must be at least 2 so
the reset-between-repetitions path is inside the measured stream.

### Geometry

179x66 (`CANONICAL_GEOMETRY`), which is the 66-row by 179-column pane `39/F1`
and `39/F3` were taken at. The identity carries it.

## Invariants

- I1. For `unicode` and `unique_unicode`, the Swift payload is byte-identical
  to what `main.go` at the pinned kitty revision generates.
- I2. For `ascii` and `csi`, the payload is a deterministic function of the
  fixed seed: two generations on any machine produce identical bytes, the
  size, alphabet, chunk strings, and band widths match `main.go`, and the
  draws are uniform over the same ranges.
- I3. Every arm's stream carries the three portions in the order above,
  with `R` payload+reset pairs and the three-`\x1b[5n` tail in the timed
  portion; feeding it into a fresh `Terminal` runs on the alt screen for the
  whole timed portion and ends back on the primary screen. The setup and
  teardown bytes match what the pinned kitty `tools/tui/loop` source emits.
- I7. Both arm binaries of one collection receive byte-identical fixture
  input, generated once from the collection's immutable root; the measured
  time excludes the setup and teardown portions.
- I4. Each `kitten-feed-*` block is validated under the `terminal-feed`
  contract (fresh 179x66 terminal per execution, one sample per block,
  1 s floor, state probe consistent) and labeled with an identity that names
  the arm, `R`, the seed, the geometry, and a SHA-256 digest of the framed
  fixture bytes including the setup/timed/teardown boundaries. Any change to
  the generated bytes or the boundary placement -- an RNG swap, a kitty pin
  that moves the wrapper, a seed change -- changes the identity, so a rule
  frozen for one stimulus can never judge another. A block collected under
  another identity fails validation.
- I5. The four names are in `CANDIDATE_WORKLOADS`, not `WORKLOADS`: the
  candidate screen accepts them, the paired comparison issues no verdict for
  them, and no entry exists in `DECISION_RULES` until a human adds one from
  a confirmed screen.
- I6. The tooling suite fails when the reference `main.go` no longer matches
  what the port encodes, and reports "reference absent" (exit 0, with the
  reason) rather than passing silently when `references/kitty` is not
  checked out.

## Proof obligations

- PO1 (I1). A test regenerates the two deterministic payloads independently
  of the port's code path -- from the string constants and loop rules as
  written in `main.go` -- and compares bytes and lengths. Lengths are known
  from the reference: `unicode` is 1024 x (lorem + misc + `\n\t`) bytes;
  `unique_unicode` is 262,144 cells of `a` plus three 2-byte marks.
- PO2 (I2). Two generations of `ascii` and `csi` are equal; every byte of
  `ascii` is in the alphabet and the length is 2,097,165; `csi`
  ends in `\x1b[m`, has length >= 1,048,593, and is a concatenation of the
  seven chunk strings and alphabet runs of 1-72 bytes. A different seed
  gives different bytes. Over the fixed seed, the observed distributions
  match the specified ones within a stated tolerance: each indexed alphabet
  entry's frequency is near 1/88 (so space, which appears twice in kitten's
  `ascii_printable`, is near 2/88), each `csi` category's share is near its band width
  (10/20/10/10/10/20/20 percent), and the ASCII run lengths are near uniform
  on 1-72. A generator that is deterministic but skewed fails this.
- PO3 (I3, I7). Feeding each arm's three portions into a fresh
  `Terminal(columns: 179, rows: 66)` leaves the terminal on the primary
  screen with the cursor visible; after setup alone the alt screen is active
  and the cursor hidden; the `Running: <desc>` line appears with the arm's
  exact description string. A harness test with an injected clock shows the
  reported duration covers only the timed portion of a fixture whose setup
  and teardown are present.
- PO4 (I4, I5). Validation tests in the shape of the existing
  `terminal-feed` collector tests: a `kitten-feed-*` block with the wrong
  identity, a short block, or a changed state is invalid; the four names are
  candidates and screenable; the manifest and block contracts freeze the
  four entries; two fixtures that differ in one byte or in a boundary
  position have different identities. A harness-level test runs the generate command and the
  measurement path for all four names, checks each reported identity, and
  checks a per-arm characteristic of the generated bytes (the description
  string and the payload length) so a routing error that maps a name to
  another arm's stream fails. The collector test shows both arms receive the
  same bytes for one collection.
- PO5 (I6). The tooling lint's self-test (in `scripts/tests/`, like
  `kitty-parity-lint_test.sh`) pins both directions: a modified copy of the
  reference constants fails, in `main.go` and in the `tools/tui/loop`
  source alike; the pinned reference passes; a missing reference reports
  absence and exits 0.

## Tooling check: the port against the reference

This is `39/D1`'s "ideal beside it". Two layers, both in one script under
`just test-tooling`:

1. **Constant parity.** The lint parses `main.go` for the alphabet, control
   chars, the two Unicode blocks, the three size expressions, the combining
   count, the seven `csi` chunk strings with their bands, the four
   description strings, the clear/reset strings, and the `\x1b[5n` count,
   and parses the pinned `tools/tui/loop` source for the bytes the
   alt-screen state set/reset and the `DECTCEM` set/reset emit. It asks the
   Swift port for the same parameters (a describe command on the benchmark
   executable prints them as JSON) and compares. Extraction by parsing
   keeps the check behavioral: it reads what the port *does*, not how the
   Swift file is laid out.
2. **Pin hash.** The lint records the sha256 of `main.go` and of the
   `tools/tui/loop` files that define those sequences, at the pinned kitty
   revision, beside the port (the same citation form `kitty-parity-lint.py`
   uses) so a pin bump that touches anything the parser does not extract
   still surfaces as a failure to re-read.

`tools/tui/loop` is not in the kitty sparse cone today; the change adds it
in `scripts/fetch-references.py`, as `39/D1` added `tools/cmd/benchmark`.

Cheaper alternative, rejected: the hash alone. It notices the reference
moving but never notices the port being wrong, which is the failure `D1`
wanted covered.

## The A/A series and the frozen threshold

Per `agent-docs/measurement-discipline.md`:

1. After the arms land, run
   `scripts/terminal-benchmark-candidate-screen.py --workload
   kitten-feed-<arm> --revision <rev>` for each of the four arms. The screen
   binds both physical arms to one immutable root and reports the rule each
   mode implies. Record each report path in `39/findings.md` as a finding.
2. Re-run the selected cell for each arm with fresh seeds (a screen is not a
   freeze; verify per series, not only pooled).
3. A human moves each surviving rule into `DECISION_RULES` and the name from
   `CANDIDATE_WORKLOADS` into `WORKLOADS`. That is Phase 2 task 2 and a
   separate commit; this plan does not freeze anything.
4. If an arm's screen selects no cell at any pair count, it stays a
   candidate and Phase 3 records its numbers as descriptive, as
   `synchronized-frames` does. Do not lengthen `R` to buy a rule without a
   finding that the noise is additive for this arm.

## Non-goals

- No PTY-path arm. `H5` is rejected (`39/F3`): delivery is 3% of the thread.
- No `long_escape_codes` or `images` arm; DanTerm already beats Ghostty on
  both.
- No fix to `Terminal` (Phase 3). No `--with-scrollback` variant; that
  changes the scroll branch and would be a different arm.
- No reproduction of kitten's writer spin or its `\x1b[0n` read loop; they
  are the writer's cost, not the terminal's.
- No frozen rule in this change.

## Accepted risks

- AR1. The random arms are not bit-identical to any kitten run. Accepted
  by `39/D1`: no such run exists to match, and a seeded uniform draw over
  the same alphabet and bands is the same stimulus statistically.
- AR2. `R` is smaller than kitten's 100. The measured quantity is
  per-execution feed time of a stream with the same structure; if a Phase 3
  fix moves the headless arm and not the kitten run, `39` Phase 4 will show
  it and the repetition count is the first parameter to revisit.

## Rejected ideas

- RI1. Add the four streams as corpora in `benchmarks/fixtures/terminal-app.json`
  under the existing `terminal-feed` workload. `terminal-feed` feeds the
  whole corpus as one block, so the arms would share one verdict and dilute
  each other; and the corpus format is bytes or `{template, repeat}`
  segments, which cannot express a seeded random draw.
- RI2. Record one kitten run with `danterm pane tape` and commit it. 200 MiB
  per arm and one frozen random draw (`39/D1`).
- RI3. Port the generator in Python. Two definitions of the stream (Python
  for the ladder, Swift or nothing for profiling); the Swift port generates
  once per collection and the Python side only frames and feeds it.
- RI4. Generate the stream inside each measured binary. Breaks the ladder's
  one-immutable-source rule: a candidate could parse different bytes than
  the baseline under the same identity and take a false verdict.

## Implementation discretion

- Where the generator library lives (a new `lib/TerminalCore` target versus
  `TerminalCoreBenchmarkSupport`), the spelling of the generate and
  describe commands, and how the framed stdin marks the untimed setup and
  teardown, provided the Python runner passes only the arm name to generate
  and reads the same measurement JSON shape.
- The seeded RNG algorithm, provided it is fixed-seed, platform-independent,
  and its seed appears in the identity.
- The value of `R` (>= 2) and the identity string's spelling beyond the
  fields I4 requires.

## Implementation notes

Commit 1:

- The generator lives in its own `lib/TerminalCore` target, `KittenFeedFixture`, with
  no dependency on `TerminalCore`. The arms are a byte stimulus rather than a terminal,
  and keeping them apart is what lets the parity lint treat one target as the single
  definition of what each arm sends.
- The timing boundary is a phase byte in front of every framed chunk (0 setup, 1 timed,
  2 teardown), and `decodeBenchmarkFixture` groups the chunks by phase before
  `measureFeedBatch` runs. Grouping at decode keeps the clock read count at two per
  execution; a per-chunk read would have added overhead scaling with chunk count and
  changed what the already-calibrated workloads report.
- The framing had five copies across the ladder, the profiling driver, the retained-row
  probe, and the research-33 scripts. Adding a phase byte to five copies is how a
  producer drifts from the decoder, so the encoding moved into one
  `terminal_benchmark_fixtures.frame_chunks` and every producer now calls it.
- `R = 2` and `seed = 39`, both the minimum the plan allows and both carried in the
  describe output so the collector can put them in the fixture identity.
- The RNG is SplitMix64 with Lemire's rejection bound, spelled out in the port so the
  byte stream cannot change under a dependency bump.
- PO1 is pinned with SHA-256 digests of the two deterministic payloads, computed from
  `main.go` by an independent implementation of its loops rather than from the port.
- The lint gets the port's parameters by running `TerminalCoreBenchmark describe`, so it
  needs a SwiftPM build and is registered in `STEPS`, not `LINT_STEPS`.
- Pre-existing, not introduced here: `docs-lint` fails on
  `docs/research/39-kitten-render-benchmark/decisions.md` lines 7, 9, 10, and 36, which
  cite `tools/cmd/benchmark/...` and `tools/tty` without the `references/kitty/` prefix.
  It reproduces on a clean `HEAD`. Commit 2 already edits `decisions.md`, so it should
  fix those four citations in the same pass.

Commit 2:

- The identity is a Python-side label, not something the arm binary reports. The four
  strings are frozen in `KITTEN_FEED_FIXTURE_IDENTITIES` and the collector invalidates
  any block whose collection generated a different one. That is what `I4` asks for
  without a second Swift change: the harness reads framed bytes on stdin and has no
  view of the arm, `R`, or the seed, so an identity it computed could only ever repeat
  the digest.
- `collect_terminal_feed` keeps its name and gains `workload=` / `stimulus_identity=`
  keywords. Renaming it to something arm-neutral would have been more honest, but the
  name reaches `scripts/research/33/t24-benchmark-confirm-floor.py`, and rewriting a
  closed research script to improve a name here is churn the plan does not buy.
- `kitten_feed_fixture` generates with a plain `swift run` rather than
  `--configuration release`. The bytes are a pure function of arm, `R`, and seed, and
  the immutable root a collection generates from is not one of the two measured arms,
  so a release build there would cost minutes and change nothing.
- The research README marks Phase 2 task 1 DONE against the plan path rather than a
  commit hash: the hash does not exist until this commit is written, and amending is
  not on the table.
- `decisions.md` also gained the four `references/kitty/` citation prefixes commit 1's
  notes flagged, so `docs-lint` is green again.
- The new harness-level test is ~50 s: it builds `TerminalCoreBenchmark`, generates all
  four arms for real, and feeds about 14 MB through the debug harness. That cost is the
  price of frozen digests -- nothing else in the gate runs the generator, so without it
  the four constants could go stale and only fail during a real collection.
