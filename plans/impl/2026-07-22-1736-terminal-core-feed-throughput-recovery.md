# Terminal core feed-throughput recovery

## Problem

The `styled-screen-redraw` compatible benchmark shows a 23.3x regression versus
Ghostty (Swift producer-write median 2.174s vs 93.5ms at 80x24). Two
independent 15-second textual profiles
(`.build/terminal-benchmark-profiles/2026-07-22-165505-9729/sample.txt`,
`.../2026-07-22-165705-11968/sample.txt`) agree that the serialized PTY thread
is gated by `Terminal.feed`, and that the cost splits roughly:

- ~40% damage/inspection bookkeeping: per-printed-scalar `Set<Int>`
  allocation, SipHash, and filter/union in `invalidateInspection` and
  `recordDamage` (`Hasher._hash` ~900 leaf samples plus all `Set` machinery).
- ~32% Unicode classification: up to six independent binary searches per
  scalar across separate boundary arrays
  (`GeneratedUnicodeTables.contains` ~1,270, `graphemeBreakClass` ~916), with
  the previous scalar's break class re-derived on every pair.
- ~25% allocation and copy-on-write amplification: a heap `[Unicode.Scalar]`
  per printed cell, plus a full `Terminal` value copy per 16KB PTY chunk in
  `applyOutput` solely for change detection, which forces CoW row copies on
  the next feed.
- `emitPrimaryHistoryMutationIfNeeded` rebuilds and compares the complete
  primary-history string per consumed frame: O(history) per frame.

Final-draw median (2.188s) ~= producer-write median, so rendering is not the
limiter. The fix is the engine's per-scalar constant factor, not any single
hot function.

Load-bearing premise: the four fixes are independent and general across
terminal workloads (all scripts, styled and plain output), not
benchmark-specific fast paths.

## Decision

Land the benchmark hardening and five optimization slices in order, each
committed separately after evidence:

0. **Core-only microbenchmark + jsonl comment field.** A headless harness
   that loops `Terminal.feed` over the existing committed workload byte
   corpora (`benchmarks/fixtures/terminal-app.json` via
   `scripts/terminal_benchmark_fixtures.py`'s `iter_bytes` seam) with no
   PTY or app, and records results through the existing suite staging and
   history flow into `benchmarks/results/terminal-app.jsonl`, distinguished
   by a new backend value so compatibility matching never compares it
   against app-backend records. Compatibility contract for core runs:
   `backend`, `workload`, `fixture.identity`, `buildConfiguration`,
   `toolchain`, and `machine` define comparability; app-environment fields
   that do not affect a headless `Terminal.feed` loop (`displayScale`,
   `geometry`, AC-power, and any final-draw summary) are omitted rather
   than filled with placeholders, and their absence is valid for this
   backend. The summary carries a single feed-duration metric (min/median/
   max over iterations) and that metric alone drives delta reporting for
   core records. Every history record gains an optional
   free-text `comment` field so successive records can say what changed
   even when based on dirty uncommitted trees; the field never participates
   in compatibility matching or delta selection, and existing records
   without it stay readable.
1. **Duration-stable core samples.** Keep the committed fixture bytes and
   identities unchanged, but batch independent executions of each fixture
   until every timed core sample contains at least one second of
   `Terminal.feed` work. An untimed warm-up calibrates the batch count; every
   execution in the timed batch starts from a fresh 80x24 `Terminal`, so
   repeated input cannot accumulate scrollback or inherit parser/grid state.
   Report normalized nanoseconds per fixture execution plus the batch count.
   A benchmark-method identity participates in core compatibility matching so
   the existing unbatched records remain readable history but never become a
   baseline for duration-stable records.
2. **A - damage as a bounded row bitset.** Internal damage accumulation
   becomes allocation-free and hash-free (full flag + fixed row bits);
   `TerminalDamage`'s observable behavior to consumers is unchanged.
3. **B - one packed two-stage Unicode lookup + cached look-behind class.**
   Cell width, Extended_Pictographic, Emoji_Modifier, emoji-variation-base,
   and grapheme-break class all come from a
   single O(1) two-stage table lookup generated by
   `scripts/generate-terminal-unicode-tables.py` from the same pinned
   Unicode 17.0.0 inputs with the same provenance header; the streaming
   segmenter carries the previous scalar's class instead of re-deriving it.
4. **C - generation counters for change detection.** Pending-consumer-work
   signaling and primary-history-mutation emission compare cheap monotonic
   counters instead of copying the whole `Terminal` per chunk or rebuilding
   the full history string per frame. Observable signaling behavior is
   unchanged.
5. **D - inline cluster storage in grid cells.** The common single-scalar
   cell stores its scalar without heap allocation; multi-scalar clusters
   spill. Grid semantics are unchanged.

Per-slice loop (encoded in Commit progress): implement; vet on the
microbenchmark; re-sample with `just benchmark-sample` and confirm the
profile bucket that slice targets actually shrank; verify with the full
compatible app benchmark for `styled-screen-redraw` (and
`scrollback-stream` for slice C); record confirmed jsonl entries with
comments; then share the microbenchmark, sample, and app-benchmark
results with the user and ask whether they accept them. The user's answer
is the gate: on acceptance, commit and check the box; otherwise reconvene
before proceeding. After the final slice, rerun the full four-workload
corpus and share those results the same way.

## Invariants

- I1: Unicode behavior stays pinned to Unicode 17.0.0 and deterministic;
  every scalar classifies identically before and after the table change.
- I2: Grapheme segmentation is invariant across PTY input chunk boundaries.
- I3: Wide cells and grapheme clusters remain indivisible through overwrite,
  erase, resize, selection, and reflow.
- I4: Damage remains observationally correct: every row whose rendered
  content changed since the last drain is reported (over-approximation
  remains allowed); consumers observe no API behavior change.
- I5: Consumer-work and history-mutation signaling fire in exactly the
  situations they fire today.
- I6: The terminal core stays pure and dependency-free.
- I7: Benchmark history stays trustworthy: profiled runs never enter
  committed history; records without a comment remain valid; delta matching
  ignores the comment; microbench records never match app-backend records or
  records produced by a different core benchmark method.

## Proof obligations

- PO1 (I1): an exhaustive differential test compares the new packed table
  against the current boundary-array classification for all 0x110000
  scalars before the old arrays are deleted; the official width/property and
  UAX #29 corpus tests keep passing.
- PO2 (I2, I3): existing grapheme, width, resize/reflow, and cluster
  fixtures pass unchanged across slices B and D.
- PO3 (I4): existing damage tests pass unchanged; behavioral coverage that
  printed, erased, and scrolled rows are reported after slice A.
- PO4a (I5, consumer work): a differential test drives the consumer-work
  counter and the existing `hasSamePendingConsumerWork` value comparison
  over the same stimuli and asserts they agree on every step, before that
  oracle is removed. Its stimuli cover each pending-work category
  separately and in combination -- row damage, clipboard write (including
  an empty-string clear), each coalesced semantic slot (title, working
  directory, progress) replaced by a later value, and ordered discrete
  events -- plus drain-then-mutate-again resignaling and several mutations
  while already signaled (which must not add wakeups).
- PO4b (I5, primary history): a separate differential test compares the
  history counter against `TerminalPaneSession`'s existing
  `primaryHistoryText != lastPrimaryHistoryText` check -- the actual
  oracle for `onPrimaryHistoryMutation`, which `hasSamePendingConsumerWork`
  does not cover -- over frames that leave history unchanged, change it,
  change it repeatedly within one coalesced frame, and change it again
  after a drain. Both must agree on every frame before the string
  comparison is removed; a missed emission leaves recovery holding stale
  history.
- PO5 (I6): `scripts/core-purity-lint.sh` and `just test` pass after every
  slice.
- PO6 (I7): the suite schema tests pin that `comment` is optional, excluded
  from compatibility matching, that the microbench backend value never
  selects an app-backend baseline, and that a core record missing the
  app-only environment fields is valid and still delta-matches other core
  records produced by the same benchmark method. Harness tests pin that
  calibration is untimed, each timed execution starts from a fresh terminal,
  the unchanged fixture is fed in its committed chunks, samples cover at
  least one second of feed work, and reported duration is normalized per
  fixture execution.
- PO7 (performance evidence, not a threshold): each slice produces an
  unprofiled microbench record, a `just benchmark-sample` re-sample showing
  what happened to the bucket it targeted, and a compatible unprofiled
  app-benchmark record. These are reported to the user, who decides whether
  the results are acceptable; the plan sets no numeric acceptance bar.

## Non-goals

- No ASCII-only or benchmark-specific fast paths; the two-stage table is the
  general answer to ASCII cost.
- No parser/action-stream restructuring (`[TerminalStreamAction]`
  materialization): not justified by the profile evidence (~100 own
  samples). Revisit only if a post-D profile elevates it.
- No renderer or frame-planning changes: final-draw ~= producer-write shows
  they are not the limiter.
- No change to the 10 MiB scrollback budget or retention policy.

## Accepted risks

- AR1: slice D touches cluster append/upgrade/downgrade paths, the highest
  correctness-risk area; accepted because the indivisibility invariants are
  already pinned by fixtures (PO2) and it is sequenced last.
- AR2: the packed table grows static data from ~4KB to tens of KB; accepted
  for O(1) classification.

## Implementation discretion

- Microbench executable placement, its jsonl summary metric shape, and how
  corpus bytes reach it, provided records flow through the existing suite
  staging/confirm path.
- Packed-record bit layout, stage-1 shift, and generator emission format.
- Bitset word layout and the internal spill representation for multi-scalar
  cells.
